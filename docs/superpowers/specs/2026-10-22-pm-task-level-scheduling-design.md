# iAssetsPro PM Task Library and Task-Level Scheduling Design

Date: 2026-10-22
Status: Proposed design approved in principle by product owner; this document captures the implementation contract before planning.

## 1. Purpose

iAssetsPro Preventive Maintenance must support reusable maintenance tasks, reusable PM templates, and PM schedules where each scheduled task can have its own maintenance mode, recurrence, duration, due state, and equipment operating-state requirement.

The design replaces the current assumption that one PM Schedule header recurrence applies equally to every task in that schedule. It preserves existing production data through an additive migration and keeps canonical Repairs/RWOP as the work-execution lifecycle.

## 2. Product outcomes

The PM module must let a planner:

1. Maintain a central Task Library.
2. Create tasks individually, in a multi-row bulk editor, or by Excel import.
3. Build reusable PM Templates by selecting tasks from the library or creating new tasks inline.
4. Create a PM Schedule using only a schedule title, asset, target, and ordered scheduled tasks plus schedule-level administrative fields.
5. Give each scheduled task its own TBM, UBM, or CBM planning configuration.
6. Reorder tasks without changing their master task numbers.
7. Generate work orders only for tasks that are due or deliberately bundled with due tasks.
8. Advance recurrence only for tasks actually completed and verified through the canonical Repairs workflow.

## 3. Terminology

- **Task Master**: reusable definition of maintenance work. It says what to do, not when to do it.
- **Task Number**: auto-generated, immutable human reference for a Task Master.
- **Task Sequence**: position of a task inside a template or PM schedule. It can be changed freely and is not the Task Number.
- **PM Template**: reusable ordered collection of Task Masters.
- **PM Schedule**: asset/target-specific preventive maintenance plan.
- **Scheduled Task**: one Task Master attached to a PM Schedule with its own planning and recurrence settings.
- **TBM**: time-based maintenance.
- **UBM**: usage-based maintenance driven by a meter/counter.
- **CBM**: condition-based maintenance driven by a measurement/condition threshold.
- **Equipment State**: whether equipment must be RUNNING or STOPPED while performing the task.

## 4. Task Library

### 4.1 Task Master fields

User-facing required fields:

- Task Number: system generated; read-only.
- Task Description: required text.
- Task Type: required category.

Initial Task Type values:

- Mechanical
- Electrical
- Plumbing
- Lubrication

System fields include internal UUID, plant/tenant ownership, active status, created-by, created-at, updated-at, and audit history. These fields do not alter the owner's requirement that the maintenance definition itself consists of Task Number, Task Description, and Task Type.

### 4.2 Task numbering

- Task Number is generated by the server, not the browser.
- Numbering is monotonic within the applicable tenant/plant scope.
- Deleting or deactivating a task never renumbers later tasks.
- Reordering tasks in templates or schedules never changes Task Number.
- Internal relations use UUIDs; Task Number is a stable human-readable reference.
- The first implementation may display simple numeric values such as 1, 2, 3 while preserving the ability to format them later without changing the underlying identifier.

### 4.3 Single-task creation

The Task Library page supports Add Task and Edit Task. Task Number is shown but cannot be edited. Existing tasks that are referenced by historical work orders are never physically rewritten in historical snapshots when the Task Master description/type changes.

### 4.4 Multi-row bulk creation

The Task Library page includes **Add Multiple Tasks**.

The editor behaves like a compact spreadsheet grid:

- Add row.
- Remove row before save.
- Paste multiple rows from spreadsheet text where practical.
- Task Description column.
- Task Type dropdown column.
- Row-level validation.
- Save All action.

Task Numbers are allocated by the server only after the batch passes validation and is committed.

Manual bulk save is transactional: if any row is invalid, none of the rows are created. The UI highlights each invalid row so the user can correct it and submit again without accidental partial creation.

### 4.5 Excel import

The Task Library includes **Download Excel Template** and **Import Excel**.

iAssetsPro already includes the `xlsx` package, so the import/export feature should reuse the existing dependency rather than add another workbook library.

The Excel template contains:

- `Task Description` — required.
- `Task Type` — required, with allowed values Mechanical, Electrical, Plumbing, Lubrication.

Task Number is not entered by the user in the import file because it is auto-generated by the application.

The workbook should include a short Instructions sheet explaining valid task types and that numbering is assigned on import.

Import workflow:

1. User downloads the current template.
2. User fills one row per task.
3. User uploads `.xlsx` or `.xls` if the parser safely supports it; `.xlsx` is the documented preferred format.
4. Server parses the workbook and returns a validation preview.
5. Preview shows total rows, valid rows, invalid rows, duplicate warnings, and row-specific messages.
6. Import is blocked until structural/validation errors are corrected.
7. On confirmation, all valid rows in the accepted preview are written in one transaction and receive sequential task numbers.
8. An audit record captures importer, timestamp, filename, row count, and created task IDs.

Validation rules:

- Blank rows are ignored.
- Task Description is trimmed and required.
- Task Type is normalized case-insensitively to an allowed canonical value.
- Unknown task types are errors.
- Duplicate rows within the same upload are warnings and are visible before confirmation.
- Potential duplicates against existing Task Masters are warnings, not silent auto-merges, because similar task descriptions can legitimately be reused in different contexts.
- The server never trusts browser-provided generated task numbers.
- File size and row count limits are enforced to protect the application; limits will be chosen during implementation based on existing upload conventions.

Import must never create half a batch after a database error. The confirmation write is transactional.

## 5. PM Templates

### 5.1 Template responsibilities

A PM Template defines a reusable ordered set of Task Masters. It does not own the authoritative asset-specific recurrence.

A template retains its existing high-level metadata where useful, including title and optional description, but recurrence is configured when tasks are attached to a PM Schedule.

### 5.2 Adding tasks to a template

Template editor supports:

- Search/select from Task Library.
- Multi-select existing tasks.
- Create a new task inline.
- Create multiple new tasks inline using the same multi-row task grid where practical.
- Reorder selected tasks.
- Remove a task from the template without deleting it from Task Library.

Any new task created from the template editor is first persisted as a Task Master, then linked to the template. There are no hidden template-only task definitions in the final model.

### 5.3 Template task association

A template-task association stores:

- template ID
- task master ID
- sort order
- active flag if required for compatibility

Task-specific schedule recurrence is not authoritative at template level in this phase. Future maintenance strategy/package defaults may be added later without changing the Task Master identity model.

## 6. PM Schedule header

The PM Schedule form is redesigned so the primary planning flow is:

1. PM Schedule Title
2. Asset / Machine
3. Target
4. Tasks and per-task Planning & Recurrence
5. Remaining schedule administration such as priority, department, assignee, work-order type, active state, and auto-generation controls where still relevant

### 6.1 Schedule description

The separate PM Schedule Description field is removed from the new schedule UI. The schedule uses Title as the primary text identity.

### 6.2 Asset and target

After selecting the Asset, the planner can drill into the existing asset/component hierarchy and select an optional target such as assembly, subassembly, component, or part. If no lower-level target is selected, the schedule applies to the whole asset.

The existing canonical asset/component registry remains the source of target identity; PM does not create a second component hierarchy.

## 7. Scheduled Tasks

A PM Schedule contains one or more ordered Scheduled Tasks.

Each Scheduled Task references a Task Master and stores its own planning configuration.

Core fields:

- PM Schedule ID
- Task Master ID
- Sort Order
- Maintenance Mode: TBM | UBM | CBM
- Equipment State: RUNNING | STOPPED
- Estimated Duration Minutes
- Lead Days
- Active
- Last Completed At
- Last Generated At where needed for duplicate-generation protection
- Mode-specific fields described below

The same Task Master may be used in multiple schedules with different recurrence settings.

Example:

- Task #17 Lubricate drive-end bearing on Pump A: every 30 days.
- Task #17 Lubricate drive-end bearing on Pump B: every 500 operating hours.

## 8. TBM planning

For Time-Based Maintenance, each Scheduled Task stores:

- Frequency Type: calendar/time.
- Frequency Interval: positive integer/decimal as permitted by the chosen unit.
- Frequency Unit: day, week, month, year.
- Estimated Duration Minutes.
- Next Due Date.
- Lead Days.
- Equipment State.

Completion advances only that Scheduled Task's next due date using the canonical recurrence calculator.

Date arithmetic must be calendar-safe for month/year schedules and must not approximate every month as a fixed number of days.

## 9. UBM planning

For Usage-Based Maintenance, each Scheduled Task stores:

- Frequency Type: meter/usage.
- Meter Source / Counter ID.
- Frequency Interval.
- Frequency Unit inherited/validated against the selected meter, such as operating hours, cycles, kilometres, tonnes, or production count.
- Last Completed Reading when available.
- Next Due Reading.
- Estimated Duration Minutes.
- Lead Days for notification/planning only when a projected due date can be calculated.
- Equipment State.

The authoritative due trigger is the meter reading, not a fabricated calendar date.

If usage history supports a projected calendar due date, the UI may show it as an estimate. The estimate must be clearly labeled and must not replace Next Due Reading as the trigger.

After verified completion, next due reading advances from the defined baseline using the configured interval.

## 10. CBM planning

For Condition-Based Maintenance, each Scheduled Task stores:

- Frequency Type: condition.
- Condition Source / Measurement ID.
- Comparison Operator, for example >, >=, <, <=, outside range.
- Threshold value or range.
- Measurement Unit.
- Optional evaluation/check cadence where required.
- Estimated Duration Minutes.
- Lead Days where meaningful for planning/notification.
- Equipment State.

The maintenance task becomes due when the configured condition evaluates true. An evaluation cadence may control how often iAssetsPro checks non-streaming sources, but it is not represented as the maintenance recurrence itself.

CBM is designed to integrate with current/future asset measurements, sensors, inspections, and IoT sources without creating a separate PM execution lifecycle.

## 11. Equipment State

Each Scheduled Task requires one of:

- RUNNING — the equipment may/must remain running while the task is performed.
- STOPPED — the equipment must be stationary/shut down before the task is performed.

This field is available to future shutdown planning and work bundling so planners can group stoppage-dependent tasks for the same asset/target.

## 12. Task ordering

- Task Number identifies the master task and never changes because of ordering.
- Sort Order controls execution/display order inside each template and schedule.
- Users can reorder Scheduled Tasks using drag-and-drop and/or accessible up/down controls.
- Generated work orders preserve the resolved task sequence at generation time.

## 13. Work-order generation

### 13.1 Due-task evaluation

The PM automation engine evaluates each active Scheduled Task independently according to its TBM, UBM, or CBM configuration.

A PM Schedule is therefore a planning container, not the cadence owner.

Example schedule:

- Check bearing temperature — TBM every 2 days.
- Lubricate bearing — TBM every 30 days.
- Replace oil — UBM every 1,000 operating hours.
- Investigate excessive vibration — CBM when threshold is exceeded.

The 2-day task can generate independently without forcing the 30-day, UBM, or CBM tasks to reset.

### 13.2 Bundling

On an automation evaluation cycle, due Scheduled Tasks for the same PM Schedule, asset, target, and compatible execution context may be grouped into one work order.

The initial implementation should prefer deterministic grouping of tasks that are actually due/inside their legitimate generation window. It must not pull unrelated far-future tasks forward merely to reduce work-order count.

Future optimization may offer planner-approved opportunistic bundling based on shutdown state and configurable tolerance windows.

### 13.3 Canonical Repairs execution

Generated PM work orders use the existing canonical Repairs/RWOP lifecycle for:

- assignment
- resource recommendations and requests
- materials/tools approvals
- task execution
- time/labor capture
- evidence/photos
- completion
- supervisor verification
- planner closeout
- rework

No parallel PM work-order lifecycle is introduced.

### 13.4 Historical snapshot

At work-order generation, the system snapshots the relevant task definition and schedule-planning context into the work-order task execution record. Later edits to the Task Master or PM Schedule must not rewrite historical work that has already been generated or completed.

### 13.5 Completion and recurrence advancement

Only a Scheduled Task that was actually completed and successfully verified/closed advances its recurrence state.

If a work order is reopened for rework, recurrence must not be treated as successfully advanced until the canonical Repairs closeout rules confirm completion.

For a work order containing multiple PM tasks, recurrence is advanced per completed task rather than blindly advancing the parent PM Schedule.

## 14. Proposed data model

Names may be adjusted to match Prisma conventions during implementation, but responsibilities are fixed.

### 14.1 New `PmTask` / Task Master

Fields include:

- id
- tenant/plant scope fields consistent with current ownership model
- taskNumber
- description
- taskType
- isActive
- createdById
- createdAt
- updatedAt

Constraints:

- unique taskNumber within its chosen ownership scope
- index on taskType and active state

### 14.2 Refactor `PmTemplateTask`

`PmTemplateTask` becomes primarily an association:

- id
- templateId
- taskId
- sortOrder
- isActive where compatibility requires it

Legacy copied description/type fields may remain temporarily during migration but are not authoritative after cutover.

### 14.3 New `PmScheduleTask`

Fields include:

- id
- scheduleId
- taskId
- sortOrder
- maintenanceMode
- equipmentState
- estimatedMinutes
- leadDays
- frequencyType/canonical trigger discriminator
- frequencyInterval
- frequencyUnit
- meter source fields
- nextDueReading
- condition source/operator/threshold/unit fields
- optional evaluation cadence fields
- lastCompletedAt
- nextDueDate for TBM and projected/non-authoritative display support where appropriate
- isActive
- createdAt
- updatedAt

Indexes must support due scans by active state, maintenance mode, next due date, meter source, and schedule/asset lookup.

### 14.4 Existing `PmSchedule`

`PmSchedule` remains the plan header and continues to own:

- title
- asset
- target/component
- template reference where useful
- priority
- assignment/department/work-order administrative defaults
- active state
- auto-generate settings
- ownership/audit fields

Existing schedule-level recurrence fields remain temporarily as compatibility columns during migration, then become deprecated once all production schedules have task-level recurrence.

## 15. Migration and backward compatibility

Migration must be additive and production-safe.

### Phase A: additive schema

- Add Task Master and Scheduled Task structures.
- Keep existing `PmSchedule` and `PmTemplateTask` fields intact.
- Add compatibility readers/writers.

### Phase B: backfill deterministically convertible data

- Convert existing PM template task rows into Task Masters without losing descriptions, task types, order, or historical references.
- Preserve existing template order.
- For existing PM schedules with known tasks, create Scheduled Tasks and copy the schedule-level recurrence into each task so existing behavior is preserved initially.
- Do not aggressively merge existing task rows by description because that can falsely collapse semantically distinct tasks.

### Phase C: legacy schedules that have no explicit tasks

Schedules without a deterministic task definition continue operating through the legacy schedule-level recurrence compatibility path until a planner edits/converts them. The UI clearly marks them as legacy and requires at least one Scheduled Task before saving them in the new model.

This avoids inventing maintenance instructions that were never present in the source data.

### Phase D: cutover

After migration coverage and telemetry show no active legacy-only schedules:

- stop creating new header-level recurrence data
- make Scheduled Task recurrence authoritative
- eventually remove/deprecate unused legacy recurrence columns in a later migration, not in the first release

## 16. API design

The implementation should expose clear resource boundaries rather than expand one large PM endpoint indefinitely.

Expected API responsibilities:

- Task Library list/create/update/deactivate.
- Task bulk-create.
- Task import template download.
- Task import validate/preview.
- Task import confirm.
- PM Template CRUD and task association/reordering.
- PM Schedule CRUD.
- Scheduled Task CRUD/reordering as part of schedule editing or a transaction-safe schedule endpoint.
- Due-task evaluation endpoints/services.

Bulk and import endpoints share one canonical Task validation service so single, bulk, and Excel paths enforce identical rules.

## 17. Permissions and audit

Task Library actions use PM planning permissions consistent with the current RBAC model.

At minimum, audit events should cover:

- task created
- task edited
- task deactivated
- bulk task batch created
- task import preview/confirmation metadata where appropriate
- template task added/removed/reordered
- scheduled task planning changed
- recurrence advanced by verified completion

Import and bulk creation must never bypass plant/tenant scoping.

## 19. Validation rules

General Scheduled Task rules:

- Task Master is required.
- Maintenance Mode is required.
- Equipment State is required.
- Estimated Duration must be non-negative and use one canonical storage unit.
- Lead Days cannot be negative.

TBM:

- interval > 0
- supported calendar unit required
- valid next due date required for activation

UBM:

- valid meter source required
- interval > 0
- meter unit must match/derive from source
- next due reading must be resolvable before activation

CBM:

- condition source required
- operator required
- numeric/typed threshold compatible with source required
- unit compatibility enforced where applicable

Inactive draft schedules/tasks may be allowed to remain incomplete only if the current PM UX already supports draft semantics; active auto-generating tasks must be fully valid.

## 20. Error handling and concurrency

- Server is authoritative for numbering, recurrence advancement, import validation, and due generation.
- Task bulk/import writes use database transactions.
- PM schedule edits that reorder/update several Scheduled Tasks are transaction-safe.
- Due generation uses idempotency/locking so parallel workers cannot generate duplicate work orders for the same task/due occurrence.
- Recurrence advancement is idempotent against repeated closeout events.
- Validation errors return field/row-specific messages rather than generic 500 errors.

## 21. Analytics impact

Current PM compliance analytics must be migrated from parent schedule cadence to task-level cadence.

Definitions must distinguish:

- number of active PM Schedules
- number of active Scheduled Tasks
- due Scheduled Tasks
- completed Scheduled Tasks
- overdue Scheduled Tasks
- schedule coverage/compliance based on evaluable task occurrences

Existing execution-effectiveness analytics should continue to use canonical Repairs completion, rework, downtime, labor, material, and cost facts. This redesign must not create a second source of truth for work execution metrics.

## 22. Testing strategy

Implementation follows TDD.

Required test groups include:

### Task Library

- server-generated monotonic task numbers
- single create/edit validation
- bulk create all-or-nothing behavior
- Excel parser/header validation
- allowed Task Type normalization
- import preview row errors
- transactional confirm
- tenant/plant scoping

### Templates

- selecting existing Task Masters
- creating a Task Master from template editor
- preserving Task Number while changing sort order
- removing from template without deleting master

### Schedules

- schedule title without description requirement
- asset then target validation
- multiple Scheduled Tasks with different modes/frequencies
- independent TBM next-due calculation
- independent UBM next-due reading
- CBM threshold evaluation
- RUNNING/STOPPED persistence
- reorder does not mutate Task Number

### Work-order generation

- only due tasks generate
- two due tasks can be bundled deterministically
- non-due tasks are not reset
- duplicate generation is prevented
- generated work task captures historical snapshot
- verified completion advances only completed Scheduled Tasks
- reopened/rework flow does not falsely finalize recurrence

### Migration

- existing templates/tasks preserved
- existing schedule-level recurrence copied to task level when deterministic
- legacy no-task schedules remain functional through compatibility path
- no data loss in production-shaped fixtures

## 23. Release strategy

This redesign should be delivered in controlled slices rather than one high-risk mega-deploy:

1. Task Master schema + Task Library API/UI + bulk + Excel import.
2. PM Template migration to Task Master associations.
3. Scheduled Task schema and redesigned PM Schedule editor.
4. Task-level TBM engine and compatibility migration.
5. UBM task-level engine.
6. CBM task-level engine.
7. Canonical due-task work-order generation/bundling and per-task recurrence advancement.
8. Analytics migration and retirement of legacy schedule recurrence creation.

Each slice gets focused tests, existing Repairs release gates, CI, and production verification before the next slice depends on it.

## 24. Non-goals for the first release

The first release does not need:

- full SAP-style maintenance strategy/package administration as a separate user-facing subsystem
- AI-generated maintenance tasks
- automatic opportunistic shutdown optimization
- automatic semantic merging of duplicate Task Masters

The data model must, however, avoid blocking those future capabilities.

## 25. Acceptance criteria

The redesign is complete when all of the following are true:

- A planner can create Task Masters one at a time.
- A planner can add several task rows and save them in one validated batch.
- A planner can download an Excel template, upload completed task rows, preview validation, and create the batch transactionally.
- Task Number is generated automatically and remains stable regardless of ordering.
- A planner can build templates from existing tasks or create tasks while editing the template.
- A PM Schedule requires Title, Asset, Target where applicable, and one or more Scheduled Tasks; the new UI no longer requires Schedule Description.
- Two tasks in the same PM Schedule can have different TBM frequencies and due dates.
- The same schedule can also contain UBM and CBM tasks.
- Each Scheduled Task has its own estimated duration, lead setting, equipment state, and recurrence/condition configuration.
- Due tasks generate through canonical Repairs/RWOP without resetting unrelated tasks.
- Verified completion advances recurrence per task.
- Historical work-order task text/configuration remains stable after later master edits.
- Existing production PM schedules continue to operate during migration and are not destructively rewritten.
